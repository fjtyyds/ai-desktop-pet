## 二、全自动开发的安全性

### 已生效的安全机制

1. 沙箱与权限：执行器使用 `codex exec --approve-for-me --skip-git-repo-check`（隐含 workspace-write 沙箱），写操作受限；需要真实权限的 GUI/网络操作走提权审批。
2. 审批拦截实证：协调者曾试图删除“含已验证 T-19 实现的非空分支”，被审批系统拒绝，保护了未合并成果。
3. 文件边界：任务卡“涉及文件”白名单 + `forbiddenAlways`（package.json、contracts.js、docs/API.md、PLAN/STATUS、AGENTS/DECISIONS 等）；越界 diff 自动打回。
4. 验收门禁：`npm run check` + `npm run smoke` + 任务卡状态更新 + 执行器退出码；最多 3 次尝试，失败保留证据并停止。
5. 合并纪律：合并前检查 main 干净；合并后清理 worktree、保留分支；协调者负责契约冻结与冲突合并。
6. 密钥安全：API Key 不进入 prompt/仓库；设置页密钥加密落盘（T-13）；汇报与日志均脱敏。

### 残余风险与建议

- `--approve-for-me` 的自动审查依赖 Codex 服务，不可用时会挂起（本批出现过长时间无输出，靠进程/子进程检查确认仍在工作）。
- 并发任务合并 main 会产生共享文件冲突（T-21 实例），需人工解决；建议并行任务尽量错开共享文件或合并阶段串行。
- 自动删除/重置分支有风险，删除前必须有“分支无独立提交”或“用户批准”判定（本批已加入自动清理的严格条件）。

## 三、Token 使用可能超额导致项目停摆

### 风险描述

- 每个 codex exec 会话可能消耗数万至数十万 token：单任务尝试最长 45 分钟（`attemptTimeoutMin`），输出可达数百 KB（T-23 单次尝试日志 512KB）；最多重试 3 次，单任务可能放大数倍。
- 协调者（本会话）同时承担“编排 + 观察 + 手工合并 + 文档”，长流程下上下文/token 消耗会进一步叠加。
- 一旦账户/模型 token 预算超限，任务会中途失败、会话被迫压缩或停摆（本批已出现“子代理只回等待指令”“前台等待超时但进程存活”等近似停摆现象）。

### 建议

1. 为 orchestrator 增加 token/时间预算：按任务限制 `attemptTimeoutMin`、`maxAttempts`，并在报告里记录每次尝试的耗时与输出量。
2. 分批执行：一次最多 2~3 个任务，避免长时间单会话。
3. 快速止损：连续 2 次失败即转人工，而不是默认 3 次重试。
4. 轻量模型/低推理档位用于简单任务；复杂任务（契约、重构）再升级。
5. 监控：运行中记录每次 `codex exec` 的 token 统计（CLI 的 session 输出可解析），超阈值自动暂停。

## 四、该自动化流程在其他项目中的复用性

### 可复用部分

- orchestrator 是独立 Node 脚本，核心循环通用：读任务卡 → 建 worktree → 下发需求（stdin 传 prompt）→ 等待 → 验收（边界/测试/任务卡）→ 重试 → 合并 → 报告。
- 支持 executor 抽象（codex/custom/mock）、`--no-merge`、`--auto`、resume、断点续跑、dry-run/doctor/selftest。

### 需要适配的部分

1. 任务卡格式约定（`docs/tasks/T-xx.md` 的字段与 `CARD_LABELS` 强绑定；本项目已修复标签解析，但换项目需核对格式）。
2. 验证命令（默认 `npm run check` / `npm run smoke`）与禁止文件清单。
3. 契约冻结方式（本项目为 contracts.js + docs/API.md + ADR）。
4. 环境前提：codex CLI 可运行（MSIX 打包环境需 `npm install -g @openai/codex` 并经 cmd 启动）、git worktree 可用、目录无中文/权限坑。
5. 已知缺陷：多 `--task` 参数实现只保留最后一个（已改为“一任务一进程”规避）；建议入库前修复并补 selftest。

### 复用建议

- 抽取为模板仓库：config 化任务卡模板、验证命令、契约文件；附带 README 与 selftest。
- 每个项目保留“协调者职责边界”：契约冻结、冲突合并、文档收尾必须由人/协调 Agent 把关，不能全交给自动化。

## 五、单对话处理所有线程导致的上下文过长问题

### 风险描述

- 本会话从 M0 一路处理到 M3.5，叠加并行线程汇报、多轮合并调试、orchestrator 修复，上下文量极大；压缩后依赖文档恢复事实，早期细节可能丢失。
- 表现为：重复决策、同一 bug 多轮才定位（如任务卡解析器三个嵌套问题）、响应变慢、token 放大。

### 缓解措施（已执行/建议）

1. 文档即事实（ADR-003）：任务卡、PLAN、STATUS、API.md、orchestrator REPORT 全部落盘，作为冷启动依据。
2. 里程碑/批次独立会话：编排会话只做“下发+验收+合并”，细节会话单独处理。
3. orchestrator 日志与 REPORT.md 作为机器可读事实源，避免靠记忆。
4. 每次合并后立即提交文档（本批已执行）。
5. 后续建议：M4 规划开新会话，从 PLAN/STATUS 冷启动，不沿用本会话全部上下文。
