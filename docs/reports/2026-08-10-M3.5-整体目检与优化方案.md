# M3.5 整体目检与优化方案（2026-08-10）

## 一、目检结论

M0~M3.5 功能已全部可用（T-01~T-23 合入 main，`npm run check`/`npm run smoke` 通过），但用户整体人工目检后反馈 9 类体验问题，需收尾优化后再进入 M4。

## 二、问题清单与处置方向

| # | 问题 | 处置方向 | 状态 |
| --- | --- | --- | --- |
| 1 | 全局快捷键功能冗余 | 移除全局快捷键、设置项与契约 `window.setShortcutEnabled` | 待确认（倾向移除） |
| 2 | 人格模板文字描述过多 | 模板卡片只显示“名称 + 一句话/标签”，完整描述折叠或选中后展开 | 已定（精简幅度待定） |

## 三、实现现状复核（代码级，2026-08-10）

- 全局快捷键：`src/main/main.js` 使用 `globalShortcut` + `SHORTCUT_CANDIDATES` 注册（默认开启），设置项 `shortcutEnabled` 持久化，渲染层设置页有开关（`src/renderer/chat.js` toggleWindowShortcut）；契约 `petAPI.window.setShortcutEnabled` / IPC `window:set-shortcut` 已冻结于 ADR-022。移除需协调者先改 contracts.js/API.md 并更新 ADR。
- 贴边：`src/main/main.js` 的 DOCK_* 常量：露边 10px、靠边阈值 24px、停留 500ms 触发、鼠标距边缘 64px 滑出、离开 1800ms 滑回、120ms 轮询、160ms 动画；`dockEnabled` 默认开启。体验差可能表现为自动隐藏触发过灵敏或滑出/滑回不稳定，需先与用户确认期望行为。
- 系统状态：`src/main/main.js` readSystemStatus/startSystemStatusWidgets 轮询 CPU/内存/电池并推送到渲染层 widgetsPanel；与“陪伴”产品核心偏差较大。
- 天气：`src/renderer/chat.js` 已有 `WEATHER_AUTO_REFRESH_MS = 30 分钟`、可见时启动定时刷新、手动刷新按钮、30 秒节流、失败保留缓存；用户感知不到“实时更新”，说明频率/反馈不足，建议 15 分钟 + 恢复窗口即刷新 + 更明显的“上次更新”提示。
- 窗口：`src/main/main.js` 创建 320×420、`frame:false`、`resizable:false`，故无法缩放；`src/renderer/renderer.js` 在底部 meta 显示平台/版本（`index.html` 第 580 行 footer）。
- 导出：当前入口在设置页“数据”区块（`index.html` export-md/export-json），应移入聊天工具栏；工具栏现只有设置/关闭按钮，无最小化、无导出。
- 番茄钟：渲染层 `finishPomodoro()` 一次性写入 `pomodoroNotifyAt` 信号；主进程 `consumePomodoroNotificationRequest()` 随状态轮询消费并清零后弹通知。重复弹窗说明“清零未生效”或“渲染层/主进程写入竞态”，需复现后修复，并补幂等断言。
- 人格模板：`PERSONA_TEMPLATES` 共 6 套，模板卡片（`renderTemplateCards`）展示完整描述，用户反馈文字过多。

## 四、任务拆分（已建卡 T-24~T-32）

- T-24 窗口布局：可缩放、小部件不遮挡聊天、移除底部平台/版本信息。
- T-25 工具栏：导出移入工具栏 + 新增最小化按钮（新增 `window:minimize` IPC/契约）。
- T-26 天气：自动刷新 15 分钟 + 窗口恢复即刷新 + 更新时间提示 + 失败重试。
- T-27 番茄钟：结束通知重复弹窗修复（幂等消费、清零竞态、防重复写入）。
- T-28 人格模板：文案精简（名称 + 一句话，完整描述折叠）。
- T-29 全局快捷键移除（待确认；前置：协调者移除契约）。
- T-30 系统状态小部件移除（待确认）。
- T-31 贴边体验：先确认预期行为再实现（自动隐藏 vs 靠边吸附，或仅保留位置记忆）。
- T-32 orchestrator 缺陷修复（最后执行；是否入库待用户决定）。
- Backlog：UI 大改（单独里程碑，M3.5 收尾后评估）。

实施顺序建议：P0（番茄钟弹窗、窗口布局遮挡）→ P1（工具栏/导出/最小化、天气刷新、贴边）→ P2（内容精简与功能移除）→ UI 大改立项。每个任务一个会话，先更新任务卡与 ADR 再实施。

## 五、“多线程开发/”勘察结论（2026-08-10）

- 内容：12 个旧 worktree 副本（AI桌宠-m1-chat 至 AI桌宠-m3-secure），含源码、node_modules 与各阶段项目文档快照。
- .md 判断：共 22 个去重相对路径，全部可在 main 仓库找到对应文档，无独有 .md；属于项目开发内容的快照。
- 结论：确认为项目开发内容；按用户指示暂时保留（不删除）。git 分支仍保留各任务历史，后续若需清理本地副本不影响仓库历史；是否清理待用户决定。

## 六、orchestrator 说明（供去留决策）

### 作用

`scripts/orchestrator/` 是外部自动化协调循环（Node 脚本）：读取任务卡 → 创建独立 worktree/分支 → 自动生成需求摘要并经 stdin 交给 `codex exec` → 等待并验收（diff 边界、`npm run check`/`smoke`、任务卡状态）→ 打回重试（默认最多 3 次）→ 通过后 `--no-ff` 合并 main → 清理 worktree（保留分支）→ 写日志与报告。

### 实战记录

T-19~T-23 由其全自动完成并合并（T-20~T-23 与 T-19 均已合入 main），是 M3.5 批次 5 能快速完成的基础。README 自带 doctor/dry-run/selftest，可断点续跑（resume）。

### 安全机制

工作线程不碰 main；任务卡“禁止触碰”+ 全局禁止清单（package.json、contracts.js、docs/API.md、PLAN/STATUS、AGENTS/DECISIONS 等）越界即打回；失败保留 worktree/分支；合并前检查 main 干净。

### 已知缺陷与风险

1. 多 `--task` 参数只保留最后一个（当前用“一任务一进程”规避）；
2. 无 token/时间预算统计，长任务可能消耗大量 token；
3. `--approve-for-me` 依赖 Codex 服务，不可用时可能挂起；
4. 并发任务合并 main 可能产生共享文件冲突，需人工解决；
5. UI 类验收无法纯自动化，仍需人工目检。

### 去留建议

若后续仍要“全自动批量开发”，值得入库，但应先修复多任务参数解析并补 token/时间预算（P2）；若改为“人工/半自动线程模式”，可暂不入库。是否入库由用户决定，入库前不修改。
